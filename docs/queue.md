# 高峰期排队、资源调配与等待时间

首版按班级截止前集中提交设计。提交成功就保存申请并返回任务号；排多久由实际可用卡数、前方就绪作业、占卡时长和回收进度共同决定。下文中的人数、时长、刷新周期与性能目标均为演练参数，开课前应按选课人数、真机试跑与课程政策校准。

## 先算一场课能否在截止前跑完

假设 1,000 名学生同时各提交一个已就绪作业；同一池起初全部空闲，每个作业从分配到释放恰好占卡 20 分钟。忽略提交、排队进程派发及构建开销，运行 `python queue_forecast.py` 可复现以下结果。

| 可用卡数 | 理想吞吐 | 第 65 人等多久能获得卡 | 最后一人等多久能获得卡 | 全部结束 |
| ---: | ---: | ---: | ---: | ---: |
| 64 | 192 个/小时 | 20 分钟 | 5 小时 | 5 小时 20 分钟 |
| 48 | 144 个/小时 | 20 分钟 | 6 小时 40 分钟 | 7 小时 |

在这个条件下，1,000 个作业若都要在 4 小时内结束，每张卡最多完成 12 个，至少需要 84 张可用卡。若实际只有 64 张，TA 应提前开放提交窗口、分批安排实验或协调临时容量。建议课程分别保存“提交包已确认接收”和“作业运行完成”的时间，由教师指定截止判定依据。学生应在提交时看到该规则。

## 高峰时一次申请如何流转

1. **接收**。平台发限时上传凭证，浏览器直传私有对象存储。上传完成并校验后，学生以幂等键确认提交。数据库在一次短事务中保存任务和状态事件，成功后再返回任务号。网络重试返回同一任务；同一学号再次建单返回已有活跃任务的入口。按账号限制高频提交，大班共用校园出口时避免仅按 IP 限额。
2. **构建**。自定义镜像走有独立并发上限的 CPU 构建队列。构建期间不占 NPU，也不进入 NPU 队位。课程镜像可直接就绪；幂等构建按输入摘要复用符合权限的缓存。页面分开展示“等待构建”和“等待 NPU”。
3. **排队**。每生最多一个活跃申请，每个就绪作业进入一个兼容资源池。同池按不可变的就绪时间和任务 ID 排序。新提交到队尾，重复请求保留原位，学生主动取消再提交则重新排队。长作业受课程运行时限约束。首版不因预测耗时较短而插队。
4. **派发**。每个池由一个持租约的调度负责人按序领取一批就绪任务；不同池可并行。批量不超过已知空闲卡扣除尚未反映在快照中的派发预留和单轮并发上限。数据库事务只做领取，网络调用在事务外执行。多个请求可同时在途，队位指领取顺序，实际启动时间可略有差异。资源端原子分配设备，满载作业按原序重试，整池短暂退避并加入随机抖动。
5. **完成和取消**。在队取消立即出队。已派发则等资源端确认清理再释放配额，覆盖超时、取消、上传结果和容器退出延迟。调度器重启后还原领取记录，按原任务号对账，再决定是否补发。发送结果不明时继续保留预留，防止把同一个任务同时派给两个资源端。

资源池按卡型、驱动兼容性和课程可用范围配置；硬件相同的首期只需一个池，每个池独立配置一个 v0.1 资源端地址。容量查询不要求修改现有接口。维护时先停派新任务，等在跑作业结束再摘除节点。设备失联后冻结受影响设备，恢复前先核对存量任务；只有确认原任务已停止，才能按明确的重试策略重新执行。管理员可调整池容量和暂停派发，操作原因与时间需留痕。

| 情况 | 页面示例 |
| --- | --- |
| 等待自定义镜像 | “正在构建镜像。构建通过后进入 NPU 队列。” |
| 资源池满载且历史可信 | “前方 12 个就绪作业，预计还需 15–35 分钟开始运行。更新于 14:30。” |
| 当前有空卡 | “正在安排资源，等待启动确认。” |
| 样本不足或发生故障 | “前方 12 个作业。资源状态正在核对，暂时无法估时。” |
| 排队跨越课程截止 | 显示预计开始时间范围、课程截止时间和已记录的提交时间，方便学生决定是否继续等待。 |

队位统计同池中排在本人前面的就绪作业；已领取或运行作业占用的卡反映在时间估算中。页面分别显示排队、启动、运行及回收状态。“预计等待”从当前快照算到获得运行资源，构建时长、获得资源后的环境启动和模型执行时间另列。区间随设备变化和前方作业变化而更新。

## 怎样估算等待时间

- **建立快照**。调度端汇总同一时刻的空闲卡、已占用且会重新可用的卡、在途预留、每个作业的占卡起点、就绪队列。每次派发、释放、取消、容量变化后合并刷新，另设周期性校正。浏览器读取共享快照，附最后更新时间。起步可用 15 秒一次的轮询并加随机抖动；1,000 个活跃页面约产生 67 次查询/秒，资源端仍只接收每池的集中查询。
- **测量占卡时间**。按卡型与课程作业类别收集“分配确认到清理完成”的时长，包括镜像拉取和结果写出。纳入失败、取消和超时实际占卡时间。记录长任务仍在运行的情况，以免刚开课只看完结样本、普遍低估。用户自报时长只作为分类参考。
- **计算各卡何时空闲**。对已占卡 18 分钟的作业，从同类历史中筛出超过 18 分钟的样本，再抽取剩余时长。空卡从 0 分钟起可用。按真实派发顺序，把队首逐个放到最早释放的兼容卡上，累加抽样得到的占卡时长。重复模拟，取每个作业预计开始时间的 P10、P50 和 P90；学生看取整后的 P10–P90 范围，TA 可看中位数和样本数。
- **证据不足时降级**。先用同作业同卡型样本，其次使用经试跑验证的同池基线并标注“粗估”。全新课程可先用样例项目试跑。零容量、心跳过期、预留状态无法核实、剩余时长样本不足或近期误差持续过大时，保留队位并显示原因，暂停提供数字。
- **校准**。按池和作业类别保存预测快照，和实际获得卡的时刻配对。以每个作业入队时的一次预测作为主要评估点，分别记录 P50 绝对误差、区间覆盖率、区间宽度和可估算作业占比。名义 P10–P90 以约 80% 覆盖为校准目标；对长尾、截止日拥堵以及集体拉取同一镜像等相关延迟单独回放。

仓库的 [Python 参考实现](../queue_forecast.py) 接收一个健康资源池的快照，演示同池 FIFO、条件剩余时长抽样及分位数计算。生产调度器负责生成一致快照、判断样本质量、过滤维护设备并对账；示例输出只用于验证算法。

## 上线压测与 TA 值班

| 演练 | 建议验收条件 |
| --- | --- |
| 1,000 个账号在 60 秒内确认提交，每个请求再重试一次 | 每个账号恰好一个活跃作业；提交确认 P95 目标低于 2 秒（上传文件另测）；服务重启后任务号及队位可恢复。 |
| 64 卡满载，16 卡进入维护，随后恢复 | 任一时刻每张卡最多一个作业，每生最多一张卡。退池卡停止接新作业；健康空卡可继续派发；缩容后更新等待范围。 |
| 1,000 个页面轮询，同时有大文件上传和自定义镜像构建 | 查询使用快照，资源端查询频率不随学生人数线性增加。分别测对象存储吞吐、构建积压、数据库延迟和状态更新时间。 |
| 取消风暴、派发响应丢失、调度器重启 | 无重复执行、漏单或提前释放；对账后所有申请均可追踪。故障期间页面显示最后更新时间和估时降级原因。 |
| 真实短作业与长作业混合 | 记录中位误差、覆盖率和按池最久等待；根据实测设置运行上限、刷新周期、派发速率与过期阈值，再开放全班。 |

TA 看板优先显示各池空闲、在途、运行、清理、维护卡数，以及就绪队长、最久等待、每小时到达和完成数、构建积压和心跳。到达率持续超过完成率时显示预计积压趋势；有空卡且队列持续不动时检查派发器和镜像服务；设备状态过期时暂停向受影响池新派发。若预测会跨过截止时间，由课程负责人决定增卡、提前开放或调整截止安排。
